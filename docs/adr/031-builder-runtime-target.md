# ADR-031: The builder runs on flue's Cloudflare target and the container holds no runtime

Status: accepted, 2026-09-14. Applies to `apps/orchestrator`, `packages/facade`, `infra/sandbox`,
the `builder` runtime profile in §6.3 and the execution environment in §8.3.

Does not change DR-3. DR-3 picks the harness base, flue on Pi behind the Reme facade, and never
names a build target. What this ADR amends is one sentence of §6.4's reconciliation prose:
"`builder` runtimes run flue's Node target inside the Cloudflare Sandbox, where the Postgres
adapter works directly." That sentence is now wrong, and this ADR says what replaces it.

## Context

§6.4 was written from flue's build rule: the Cloudflare target rejects a custom `db.ts` at build
time, and the Postgres adapter is Node-target only. From that it followed that a runtime which
wants Postgres persistence must run on the Node target, and the only place a Node process can run
in our shape is inside the sandbox container. So §6.4 put the Developer there.

That shape needs the container to open a connection to Postgres. Checked 2026-09-14 against
Cloudflare's sandbox outbound-traffic guide:

- "Outbound handlers only intercept HTTP and HTTPS traffic."
- "Traffic on ports other than 80 and 443 is never routed through `outbound` or
  `outboundByHost`. If you set `enableInternet = false`, that traffic is denied."
- "When `allowedHosts` is set, it becomes a deny-by-default allowlist."

Postgres speaks its own protocol on 5432. The proxy cannot inject a credential into it the way it
injects a bearer header into an HTTP request, so a flue process in the container would have to
hold the connection string itself, and the container would need internet enabled to reach the
database at all. Both break §8.3's rule that the container never holds a credential, and the
second breaks the egress allowlist. The Node-in-container shape and the security rules cannot
both be true.

Flue's own Cloudflare docs, read the same day, recommend the other shape for coding agents: the
agent is a Durable Object generated by `@flue/vite`, and it attaches a sandbox with
`useSandbox(cloudflareSandbox(getSandbox(env.Sandbox, id)))`. Secrets stay in the Worker and are
injected at the outbound proxy. The container runs commands and holds files. Nothing else.

## Decision

**The Developer agent runs on flue's Cloudflare target, in a Durable Object, the same way the
`lite` runtimes do.** One DO conversation per assignment, keyed by `assignment_id`. The DO's
SQLite is flue's execution store, and the facade tees every runtime event into the Postgres event
log, which stays the system of record. This is the reconciliation §6.4 already made for `lite`,
now applied to `builder` as well. The Worker reaches Postgres through Hyperdrive and models
through the transport the facade selects. The container reaches neither.

**The container is a filesystem and a shell.** It is attached with
`cloudflareSandbox(getSandbox(env.Sandbox, assignment_id))`, runs with `enableInternet = false`
and an `allowedHosts` list naming the npm mirror and nothing else, and holds no key, token or
connection string. The agent's tools call `exec`, read and write files, and nothing in the
container calls back into the Worker. The nanoclaw single-writer pair in §8.3 still holds: tools
write to the Workflow with `sendEvent`, the Workflow writes to the agent with a new submission.

**Site source is a snapshot per revision in R2, not a git remote.** §8.3 names a platform git
remote that nobody has created, and under this decision the container could not reach one
anyway. The sandbox still works in a real git repository, and the revision snapshot includes
`.git`. `sites/{site_id}/{revision_id}/source.tar.zst` is the source, `dist/` beside it is the
artifact, `manifest.json` beside both. A later assignment restores the latest snapshot. The
Sandbox SDK's `createBackup()` and `restoreBackup()`, shipped 2026-02-23 with backups stored in
R2, are the fast path when the container is the same; the tarball is the path that always works.

**Retention keeps two revisions per site and deletes the rest seven days after they stop
mattering.** `v{n}` is the site's own counter, so a version number means something to the owner:
v3 is live, v2 rolls back. A revision takes its number when it passes the gates, so the count
holds only versions the owner can see: a report the gates refuse keeps its row with no number,
and the attempt that passes takes the next one. A new site starts at v1, with no gaps. Every
kept revision carries its tag and the change summary the Developer wrote in
`CompletionReport.changes[]`. When a publish succeeds, the publisher marks
every revision other than the active one and the previous one `retired` with a `retire_after`
seven days out, and destroys the assignment's sandbox at once, since the snapshot makes it
recoverable. A daily sweep deletes the R2 prefix of every revision whose `retire_after` has
passed and appends one event per deletion naming the keys. A revision under review is the
candidate and is not retired until it is published or rejected; a rejected candidate enters the
same window. `site_revisions` rows are never deleted, so the summary of every version stays
readable after its files are gone.

The window is seven days for two reasons. A mistaken rejection or a rollback past `v{n-1}` is
recoverable for a week. And deletion never sits in the publish path, where a failed delete would
block a release.

## What was rejected

*Flue's Node target inside the container, with the Postgres adapter.* This is what §6.4 said.
It fails on the egress finding above: the container would hold `DATABASE_URL` and need 5432
open. It also puts the model key in the container or forces every model call through the HTTP
proxy with a header injected per host, which is workable for models but not for Postgres. The
shape is dead on the first rule it has to satisfy.

*Enable internet and allowlist the database host.* `allowedHosts` filters by host, and the
credential still has to be inside the container for the driver to present it. The rule is "no
credential in the container", not "no unexpected host".

*A hosted git remote for site source.* Nothing exists to host one, and the container could not
reach it under this decision. Snapshots in R2 carry `.git`, which is enough for restore and
audit. Open item 41 in the builder track keeps the remote as a possibility, with its trigger.

*Keep every revision.* Storage is cheap but the list is not. An owner reading "v1 through v14"
with no way to tell which matter is worse off than one reading "v3 live, v2 rolls back". Two
revisions plus a week covers every recovery case the failure model in §13 names.

## Consequences

- §6.4's `builder` sentence is replaced by a pointer to this ADR. The rest of §6.4, including
  the `lite` reconciliation and the operational cautions, stands.
- §8.3's egress allowlist for the builder container loses two entries. AI Gateway drops out
  because models are called from the Worker, never from the container. The platform git remote
  drops out because source is an R2 snapshot. The allowlist is the npm mirror only, and story Q4
  proves it on every PR.
- §8.3's "cloned from the platform git remote using a repo-scoped, 1-hour token" becomes
  "restored from the latest snapshot". No repo token exists, so none can leak.
- §8.2's "checkpoint = commit + push to platform remote" becomes commit plus `createBackup()`,
  with the tarball snapshot at revision boundaries.
- `site_revisions` gains `status` with a `retired` value and a `retire_after` column, both
  landing with the table in story M2 and used from story P4.
- A revision whose assignment was cancelled because a newer build superseded its preview is a
  rejected candidate for retention, and a `site.revise` restores from the published revision,
  never from a superseded preview. Amended 2026-09-15 with the console preview.
- The Developer's DO is subject to the Durable Object CPU limit, 30 s per invocation by default.
  The response is I/O bound, so this is expected to hold; the builder track's open item 43 says
  what happens the first time it does not.
- Spike S1 in §22, "does the facade hold without forking?", is answered by the facade story (N2)
  on this target rather than run separately.

## Change if

Cloudflare's outbound proxy starts routing non-HTTP traffic, or the Sandbox SDK grows a way to
present a credential to a TCP connection from the Worker side. Either would make the Node target
in the container possible again, and the question would then be whether it is worth having two
execution shapes. Or flue's Cloudflare target gains the Postgres adapter, at which point the DO
SQLite tee becomes optional and §6.4's `lite` reconciliation is the thing to revisit.

## Amendment, 2026-10-19: the sandbox moves to Sandbox SDK 1.0

`@cloudflare/sandbox` 1.0 no longer ships the `Sandbox` Durable Object, `getSandbox` or the
control server in the image. 0.x gets fixes until 2026-12-31, so the builder moves now. The
container is still a filesystem and a shell, with no credential and the registry as its one
host. What carries it changes:

- `RemeSandbox` (`apps/orchestrator/src/container.ts`) is our own class on `DurableObject`. It
  starts its container through `ctx.container` on `standard-2` with the Internet off, routes
  ports 80 and 443 to `SandboxEgress`, trusts the intercept CA as root, and sets the 30 minute
  inactivity timeout that was `sleepAfter`. Its methods are the ones flue's `cloudflareSandbox`
  calls on a 0.x stub (`exec`, `readFile`, `writeFile`, `exists`, `mkdir`, `deleteFile`,
  `getState`), with 0.x meanings, so flue needs no adapter and the Workflow's call sites keep
  their commands. A command runs in bash from `/workspace` with three literal variables
  (`HOME`, `PLAYWRIGHT_BROWSERS_PATH`, `NODE_EXTRA_CA_CERTS`); a timeout runs it under GNU
  `timeout` and throws as 0.12 did. Bash gets the command in a variable it un-exports, never in
  argv: as in a 0.12 session no command line holds it, so the screenshot step's
  `pkill -f '[a]stro preview'` cannot kill the shell running it (it did, in the first local
  run). Files go through `Files` and the `sandbox-shim` helper.
- `SandboxEgress` is §8.3's rule as code: `registry.npmjs.org` is fetched, every other host gets
  0.12's `520 Origin is disallowed`.
- The `durable_object` scheduling policy has no `max_instances`, so the pool of five is
  `SandboxPool`: one Durable Object (`getByName("pool")`) whose methods never await, so grants
  cannot race. A sandbox asks it for a slot before it starts a container, renews its lease at
  most once a minute while it works, and releases it on `destroy()`. A lease runs 35 minutes
  from the last call, the sleep plus slack, so a container that slept or crashed frees its slot
  by itself. A refused slot is `open()` answering false, and `provision()` keeps its path:
  evict the least recently edited warm sandbox, else `PoolExhaustedError` and `pool.exhausted`.
- The image is `node:22-trixie-slim` with the tools, fonts, Playwright, pnpm and `/opt/astro`
  the 0.12 base gave us, plus `sandbox-shim` from `cloudflare/sandbox:1.0.1`.

What behaves differently:

- Nothing carries from one command to the next. Every call site already changed directory
  inside its own command, and flue passes the working directory on every call.
- A command that times out is stopped with everything it started. 0.12 threw and left it
  running.
- Under this policy every process has root's capabilities, whatever its user. The `reme` user
  now only sets who owns new files, so file permissions no longer keep a command off `/opt`.
  The egress rule and the no-credential rule are enforced outside the container and still hold.
- `output()` waits for every process that holds the command's output open, so a command that
  backgrounds a process must redirect its output, as the screenshot script does.
- A container that stops under a call surfaces as flue's `sandbox_died`, which the turn gate
  maps to `sandbox.updating` as it did `OPERATION_INTERRUPTED`.
- A deploy no longer restarts running containers, and a new image reaches only containers that
  start after it. A slept container also holds its slot for up to five minutes past its sleep.

### Staging rehearsal and production cut-over

The deploy that moves `RemeSandbox` to `scheduling_policy: "durable_object"` cannot be undone.
After it, 0.12 code cannot start containers for the class, and `wrangler rollback` to a 0.12
version deploys code that cannot build a site. Do not roll back. Every fix is forward.

1. Build the image from the release commit and run the in-image check (sharp, astro,
   `@axe-core/playwright` from `/opt/astro`, the font count):
   `docker build --platform linux/amd64 -t reme-sandbox:sdk1-<date> infra/sandbox`.
2. Push it: `cd apps/orchestrator && FORCE_COLOR=0 pnpm exec wrangler containers push
   reme-sandbox:sdk1-<date>`. Put the printed digest in both `images.sandbox.image` entries of
   `apps/orchestrator/wrangler.jsonc` and land that. Until then they pin the 0.12 image, whose
   entrypoint is the old control server and which has no `sandbox-shim`: 1.0 cannot run on it.
3. On staging, leave a sandbox running: build a site to `preview_ready`, so a warm sandbox exists
   at the switch, as one will in production. Note `wrangler containers list`.
4. Deploy with `stage.sh`, which waits until no assignment or publish instance is live.
5. Check, in this order:
   - `wrangler containers list` shows `reme-orchestrator-sandbox-sdk1` beside the old
     application, which Wrangler named from the Worker and class.
   - `ORCHESTRATOR_URL=https://staging-orchestrator.remeai.co.uk ORCHESTRATOR_TOKEN=<token> pnpm
     --filter orchestrator test:probe` passes all five cases: the public internet refused, the
     registry 200, no secret in `env`, the Astro build, a cold start.
   - A change to the site from step 3 reaches `preview_ready`. Its container is new, so the
     build restores from R2 and `sandbox.provisioned` shows a cold start; screenshots land and
     the a11y gate runs.
   - A new site's first build reaches `preview_ready`.
   - Worker logs show no `sandbox.lease_failed` and no error from `RemeSandbox.alarm`.
6. Delete the old staging application: `wrangler containers delete <old application id>`. It
   bills until then.
7. Production: the same steps against `CLOUDFLARE_ENV=production` and the production URL, at a
   time with no live `reme-assignment-production` or `reme-publish-production` instance. The
   pushed image serves both, since one registry holds it. The new application is
   `reme-orchestrator-production-sandbox-sdk1`.

If a check fails after the switch, builds fail at their `sandbox` step and end `failed`, which
releases the site lock; published sites are untouched, because the router never reads a
container. Read the Worker logs for the failing call, fix forward and deploy again:

- No container starts, or `Files` calls fail with a protocol error: the image. Fix the
  Dockerfile, rebuild, push, move the pin.
- Every call fails with "did not trust the intercept CA": the CA never appeared. Check that
  `interceptOutboundHttps` is registered before `TRUST` runs.
- The registry probe fails and the denied probe passes: `SandboxEgress`.
- Builds wait on `pool.exhausted` with nothing running: leases are not being released. Slots
  free themselves 35 minutes after their last call; a forward fix is `SandboxPool`.
